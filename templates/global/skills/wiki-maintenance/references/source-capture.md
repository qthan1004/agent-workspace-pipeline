# Retain and retrieve sourced knowledge

Use for documents, API references, supplied files, links, architecture notes or other material the user wants agents to reuse. Organize around the existing project/domain and likely future questions. The source's format does not decide whether it also contains policy or a useful procedure: consult pipeline's context-maintenance reference when purposes overlap.

Inspect existing wiki MAP/INDEX and source captures; update the closest bounded context rather than creating a page per endpoint/file/chat. Keep a concise entry page and meaningful path/symbol/tag/description routing. Link related contexts and existing technical docs. Store an original source once under the existing `.agent/raw/<context>/` when capture is needed; avoid a separate folder taxonomy for every tool or workflow.

Read the actual supplied source. If a link is inaccessible, preserve it with the known limitations and keep unsupported claims draft; do not invent its contents. Capture origin, upstream version when available, date, repo-relative file and SHA-256. For a page verified against captured files, use `verification_scope: documentation` or `source`, and `verified_sources` entries with `file`, `sha256`, `origin`, `captured_at`. Keep `verified_against` empty when no actual Git revision was inspected. Snapshot hashes prove which local material was reviewed, not current upstream freshness or runtime behavior.

Curate facts, invariants, relevant flow/relationships, source entrypoints and practical verification entrypoints with their limits. A Swagger/OpenAPI example might keep operationId/method/path, request/response/error contracts, authentication requirements, related operations and existing test location. Include only supplied/verified behavior. Credentials stay outside the knowledge page; a documented authentication scheme is not an available credential. These examples are optional content based on the future use, not a universal page template.

Saving references for future testing authorizes capture/curation, not endpoint calls or implementation. Later, when testing is actually requested, resolve the context with intent plus domain/operation/path, read original contracts only as needed, check source freshness and inspect existing client/tests. Use the relevant test procedure and observe its actual environment/authorization. Avoid loading every raw document into every task.

Release a substantive page with owner, version, date, active status and verified revision or reviewed source hashes; the release checks captured file integrity. Update MAP and the human-readable INDEX links in the same maintenance change. Confirm a realistic future query selects it. The resolver excludes pages with changed/missing captured sources; check-stale reports local drift and explicitly leaves upstream freshness unchecked. Refresh/review affected statements before re-release, rather than restamping hashes alone.

If sourced facts change, revise the wiki. If intended working constraints change, revise the applicable rule too. If an existing rule remains valid, link it rather than copying it into wiki. Improve a procedure only when its future use warrants it. Findings during product execution stay proposals until maintenance is authorized.
