# Source audit and adoption decisions

Reviewed 2026-10-05. This records design inputs, not executable instructions from other repositories. The product remains a portable layer of rules, skills, contracts and evidence for an existing harness. Users converse or provide plans; the agent handles internal task operations. The user's requested outcome and authorization take precedence over borrowed workflows.

## Scope and method

Read the supplied plan and conversation summary, personal skill entrypoint, the common skill entrypoints, Harnix's general workflow and relevant planning/implementation references, and the two supplied wiki images. For each repository below, inspect its README and public skill where present; follow relevant authority, readiness, review, memory and runtime references. Pin snapshots so later upstream changes cannot silently change this review. This is a product/workflow review, not an exhaustive implementation or security audit of every upstream file.

The [Kun profile](https://github.com/kunchenguid) was also scanned for related tools. AXI and `axi` refer to the same repository. Dotfiles, acp-mock and superpowers-bench add relevant context; unrelated applications, platform launchers and archived projects are not package dependencies.

## Resulting gates and verification

| Demonstrated gap | Change | Verification |
| --- | --- | --- |
| Screenshot-only request becomes an invented product/stack/flow | Core and intake skills require an intent/context checkpoint; ask about unresolved consequential choices; record decision provenance. | Behavioral scenarios and scoped fixture observations in [behavioral-evaluation.md](behavioral-evaluation.md); runtime tests verify unresolved discovery cannot approve/non-draft prepare/run. |
| Agent-authored task is treated as evidence of user decisions | Discovery records outcome, actual input/source references, affected flow and sourced/delegated decisions; review challenges provenance as well as implementation. | Contract changes invalidate approval; legacy contracts can be read/revised but need discovery before execution. These checks do not authenticate conversation truth. |
| Review feedback changes a shared default without checking other consumers | Conditional review-feedback reference requires causal/source/caller inspection and regressions for affected and preserved paths. | Fresh review remains bound to current source and contract. Semantic review quality still requires an actual independent reviewer. |
| Updated package leaves old default CORE/skills installed | Explicit refresh updates only recognized pristine shipped defaults; customized knowledge is preserved and reported. | Upgrade, custom preservation, idempotency and execution-lock tests; packed installation smoke. |

External tools remain optional. Installing this package does not install Kun's ecosystem, log into providers or create a new runtime. The adopted invariants operate through the user's existing harness.

## Existing-project case study

The user also supplied an existing checkout application as a local case study. Read its personal/coding skill entrypoints and representative responsive-planning, connectivity-recovery and dynamic-method technical documents, then spot-check the documented recovery boundary against current source. Its semantic index was stale and keyword lookup reported missing FTS indexes, so source reads supplied the check; the case study was not modified or reindexed.

Useful general patterns: inspect established stack and flow rather than ask users for discoverable facts; compare current versus requested behavior; name data/state owners and preserved defaults; map implementation slices and acceptance to test/runtime cases; keep final technical docs aligned with real code. A source spot-check is not proof that the application's entire implementation or earlier conversations met every requirement.

These patterns inform the plan technical-handoff reference and pipeline/review guidance. Private business logic, credentials, absolute paths, arrow-function policies and local artifact firewalls are not copied into the portable package. The case study is a quality reference, not a target for changes or a preset product stack.
